# 协议记录 —— HECATE G5 MAX 底座版

抓取环境：Windows 11 25H2 (Build 26200.9711)，HECATE 驱动 1.1.44，
设备 `USB\VID_35BB&PID_A228`（无线底座版）。

以下内容全部来自对 HID 报文与注册表的观测，**不是厂商文档**，仅供参考。

---

## 1. 设备结构

`VID_35BB&PID_A228` 是一个 USB 复合设备，底座同时承担 2.4G 接收器与充电座：

| 接口 | 类别 | 说明 |
|---|---|---|
| `MI_00` | MEDIA | USB 音频（`HECATE G5 MAX底座版`）。只要底座插着，该端点就一直存在，Windows 因此感知不到设备变化 |
| `MI_03` | HIDClass | 厂商自定义，65 字节报文（report ID + 64），固件升级通道，帧头 `00 4A 4C`（ASCII "JL"）|
| `MI_04 Col01` | HIDClass | 消费类控制（音量/播放键），3 字节 |
| `MI_04 Col02..05` | HIDClass | 厂商自定义，64 字节 |
| `MI_04 Col03` | HIDClass | **设备控制通道**，状态帧从这里推送 |
| `MI_04 Col04 / Col05` | HIDClass | 耳机灯效 / 底座灯效 |
| `MI_04 Col06` | HIDClass | 电话类（USAGE_PAGE 0x0B, USAGE 0x05 Headset），3 字节 |

驱动安装目录下，每款设备有一份纯文本配置（`data/devices/` 下），按功能列出了该设备使用的 HID 通道。
下表是对该配置内容的**转述**（未复制原文），仅用于说明通道用途划分；下文的报文观测可以独立得出同样的结论：

| 用途 | 通道 |
|---|---|
| 设备控制（本工具使用） | `MI_04 & Col03` |
| 耳机灯效 | `MI_04 & Col04` |
| 底座灯效 | `MI_04 & Col05` |
| 无线 / 有线变体 | 由设备 PID 区分（无线 `A228`，有线 `A229`）|

## 2. 帧格式（`MI_04 & Col03`，64 字节，无 report ID）

```
D0 35 BB <cmd> <sub> <payload...> ... 04
│  └──┴── VID = 0x35BB（小端）
│
└─ 固定帧头
   <cmd> 命令号
   <sub> 子命令 / 保留
   末字节恒为 0x04（不是校验和，各命令下都是 0x04）
```

### 2.1 `0x0A` —— 状态帧（核心）

载荷（第 5~10 字节）有两种取值：

| 场景 | 载荷 | 含义 |
|---|---|---|
| **使用中** | `01 64 00 01 01 09` | `0x64`=100 电量；有完整遥测 |
| **在底座上** | `00 00 00 00 00 00` | 耳机已关机，读不到任何遥测 |

完整帧示例：

```
使用中   D0 35 BB 0A 00 01 64 00 01 01 09 01 01 03 ... 04
在底座   D0 35 BB 0A 00 00 00 00 00 00 00 01 01 03 ... 04
```

### 2.2 `0x03` —— 状态帧（旁证）

```
使用中   D0 35 BB 03 EF 00 01 ...
在底座   D0 35 BB 03 01 64 01 ...
```

第 5 字节：`EF` = 使用中，`01` = 在座。与 `0x0A` 的结论始终一致，可作为交叉校验。

### 2.3 `0x07` —— 读取 MAC

```
D0 35 BB 07 02 6C 16 29 A9 FA 2F ...
```

载荷为 6 字节 MAC（示例 `6C:16:29:A9:FA:2F`）。

## 3. 关键陷阱（踩过的坑）

### 3.1 不要主动查询，只能被动接收

主机主动写入 `D0 35 BB 0A 00 ... 04` 时，底座**会**回应一个 `0x0A` 帧，
但回应内容是与耳机状态**无关的过期记录**：

```
主动查询恒为: D0 35 BB 0A 00 00 64 01 00 00 00 01 01 03
              （注意是 00 64 01，和真实的两种状态都不同）
```

这个过期值不随耳机状态变化，曾被误判为"固件无法区分在座/使用中"。
正确做法是只读推送帧。**本工具的早期版本就是因为主动轮询而长期跑错。**

### 3.2 状态映射容易搞反

- `00 00 00 00 00 00`（全零）→ **在底座**。直觉上会以为是"没有数据=异常"，实际是关机状态的正常表现。
- `01 64 00 01 01 09` → **使用中**。曾因为第 5 字节像"充电标志"而误判为在座。

### 3.3 别用 `pnputil` 停用音频接口

用 `pnputil /disable-device` 停用 `MI_00` 也能让端点消失，但：

- 需要管理员权限
- 反复 disable/enable 会把设备推进"等待系统重启"状态（`pnputil` 报 exit 50）
- 拆掉 USB 音频接口会让底座自身状态发生变化，导致状态误判、自激振荡

正确做法是 `IPolicyConfig::SetEndpointVisibility`（即声音设置里的"禁用设备"），
只影响端点可见性，不碰 PnP，不需要提权。

### 3.4 推送是事件驱动的

状态帧只在状态变化时推送，没有周期性心跳。因此：

- 错过一次推送 → 状态会滞后到下一次推送
- 启动时若尚未收到推送，用 `last-state.txt` 里的上次状态先恢复一次
- 每秒执行一次校正，避免 Windows 自行改变默认设备后不恢复

## 4. 设备路径的发现方式

HID 接口路径形如：

```
\\?\HID#VID_35BB&PID_A228&MI_04&Col03#7&268607c4&0&0002#{4d1e55b2-f16f-11cf-88cb-001111000030}
```

其中 `7&268607c4&0&0002` 是 USB 枚举时生成的实例哈希，**换机器/换口就变**，不能写死。

正确做法是遍历注册表：

```
HKLM\SYSTEM\CurrentControlSet\Control\DeviceClasses\{4d1e55b2-f16f-11cf-88cb-001111000030}
  └─ ##?#HID#VID_35BB&PID_A228&MI_04&Col03#7&...&0002#{guid}
```

键名把路径里的 `\` 换成了 `#`，开头的 `##?#` 对应 `\\?\`。还原：

```csharp
"\\\\?\\" + keyName.Substring(4)   // 只把前 4 个字符 "##?#" 替换掉，其余 # 保留
```

音频端点同理，不能写死 GUID，应遍历 `MMDevices\Audio\Render`，
用属性 `{b3f8fa53-0004-438e-9003-51a46e139bfc},6`（DeviceDesc）做前缀匹配。

## 5. 复现方法

```powershell
G5DockSwitch.exe --probe          # 自动发现结果 + 监听 3 秒
G5DockSwitch.exe --capture 60     # 录 60 秒原始帧到 capture.log
```

抓取时反复"拿起 → 放回"，即可看到 `0x0A` 与 `0x03` 在两种状态间切换。
